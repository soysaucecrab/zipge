# 미제스코리아 검색 시스템

브라우저에서 완결되는 하이브리드 검색(키워드 + 형태소 + 시맨틱)과
문서 그래프 기반 관련 글 추천. 서버(RAM 1GB)는 정적 파일만 내보내며
검색 연산에 관여하지 않는다.

## 1. 쿼리 처리 순위

검색어 하나가 들어오면 아래 순서로 처리·서열화된다. 원칙은
**"추론 최소화 — 문자 그대로가 항상 추론을 이긴다"**.

| 순위 | 층 | 조건 | 예시 |
|---|---|---|---|
| 1 | **리터럴 일치** | 쿼리가 제목에 통째로 포함 | "자유와 반공을 위해" → 동명 제목 글이 무조건 1위. 이 경우 교정도 발동하지 않는다 |
| 2 | **형태소 일치 (T0)** | 명사 단위 일치 (조사·어미 무시, 자모 1글자 오타 흡수) | "인플레이션의 원인" → 인플레이션+원인 제목 글 |
| 3 | **시맨틱 유사 (T1)** | 임베딩 코사인 유사도 | "자유시장 경제는 왜 옳은가" → 의미가 가까운 글 |
| 4 | **오타 교정 후 재시도** | 1~3이 모두 빈약할 때만 (최후수단) | "쎄금" → "세금"으로 자동 재검색 + 원문 검색 링크 제공 |

층위 간 최종 서열은 **융합 정책**이 정한다:

- 짧은 쿼리(≤3토큰)에서 키워드 증거가 강한데(top 정규화 점수 ≥0.65)
  시맨틱 상위 10건과의 겹침이 30% 미만이면 → **키워드 주도**
  (오타 임베딩 노이즈 방어). 긴 쿼리는 기준을 0.9로 올려 자연어
  질문이 시맨틱 주도로 남게 한다.
- 교정문으로 임베딩한 경우는 시맨틱을 신뢰한다(노이즈 원인이 제거됨).
- 주도 층이 앞서고 다른 층이 뒤를 채우며, id로 중복 제거.

화면 구성: 상단 블록 = 위 관련도 순위(최대 8건, 서버 목록과 겹치는
글은 **하단 목록 쪽에서** 제거 — 관련도 순위에는 구멍을 내지 않는다),
하단 목록 = 서버(PocketBase LIKE) 결과의 날짜순 전체 목록 + 페이지네이션.

**정렬**: 검색어가 있으면 기본은 **연관순**(위 융합 순위 그대로).
최신순·오래된순·인기순(조회수)을 고르면 **재검색 없이** 이미 가진
융합 결과 집합을 클라이언트에서 재정렬만 한다 — 임베딩도 다시 돌지
않는다. 하단 서버 목록은 연관도를 모르므로 연관순일 때 최신순으로
깔리고, 다른 정렬은 서버 정렬(`ARTICLE_SORT_MAP`)을 그대로 쓴다.

## 2. 자산 위치와 접속 흐름

**모델·인덱스 위치** — 전부 이 레포 `static/`에 있고 Docker 이미지에
포함돼 같은 오리진에서 정적 파일로 나간다. 서버는 전송만 하고 추론하지
않는다.

| 자산 | 위치 | 크기 | 받는 시점 |
|---|---|---|---|
| 가지치기 e5-small (ONNX+토크나이저) | `static/models/e5-small-ko/` | 37MB | 첫 검색 시 (이후 브라우저 캐시) |
| garu 형태소 분석기 (WASM) | JS 번들 에셋 | 1.6MB | 첫 검색 시 |
| 문서 벡터·메타·태그 | `static/search-index/` | ~0.7MB | 첫 검색 시 |
| 폴백 사전 `terms.json` | `static/search-index/` | 64KB | WASM 차단 시에만 |
| 폴백 어휘 벡터 | `static/search-index/` | 1.8MB | 모델 실패 시에만 |
| 관련 글 인덱스 | `src/lib/server/data/` (서버 번들) | 1.4MB | SSR (사용자 다운로드 없음) |
| HF 허브 원본 모델 | 외부 (Xenova/…) | 118MB | 로컬 모델 실패 시에만 |

**사용자 접속 흐름**:

```
① 사이트 방문 (검색 안 씀)
   → SSR HTML + 기본 JS만. 모델·인덱스 다운로드 0.
     글 페이지 "관련 글"도 SSR이라 추가 비용 없음.

② 첫 검색 실행
   → [즉시]   서버 목록(제목 LIKE, SSR) + 메타 기반 부분 문자열 T0
   → [~1초]   garu 로딩 → 형태소 매칭·오타 교정으로 T0 업그레이드
              (교정 시 서버 목록 자동 재조회)
   → [백그라운드] 워커 모델 사다리: WebGPU → WASM 로컬(37MB, 최초
              1회 ~4초) → WASM 허브. 문서 벡터 병렬 fetch.
   → [준비 완료] 쿼리 임베딩 → 시맨틱 결과로 승격 (융합·게이트)

③ 이후 검색 → 전부 캐시 히트, 임베딩 수십 ms + 내적 1ms

④ 수명 관리 → 10회마다 워커 재활용, 3분 유휴·페이지 이탈 시 해제

⑤ 실패 시 → §8 폴백 (사전·합성 임베딩), 서버는 끝까지 추론 없음
```

원칙: 검색을 안 쓰면 비용 0(지연 로딩), 서버는 정적 전송만, 무거운
것일수록 뒤로 — 화면은 항상 즉시 반응하고 점진적으로 좋아진다.

## 3. 검색 층위 상세

### 리터럴
`meta.title.includes(정규화된 쿼리)` — 점수 1.5로 어떤 매칭(최대 1.0)보다
위. 존재하면 교정 전체가 비활성화된다.

### T0 — 형태소 키워드층 (`src/lib/search/korean.ts`, `core.ts`)
- **garu**(한국어 형태소 분석기, Rust→WASM 1.6MB)로 쿼리와 문서(제목·
  태그·저자)에서 명사 추출. 임베딩 모델보다 훨씬 먼저(~1초) 준비된다.
- 쿼리는 세 갈래로 해석해 최고점을 취한다: 명사 세트 / 표면형 토큰 /
  공백 제거 결합형("세 금"→"세금"). 명사 세트는 단일 토큰 쿼리에서
  커버리지 70% 미만이면 불신(미등록어 파편화 방지).
- 단어 매칭 규칙(`termsMatch`): 같음(1.0) > 포함(0.9, 양쪽 2자 이상,
  쿼리가 삼키는 방향은 60% 이상 덮을 때만) > 자모 편집거리 오타(0.7)
  > 접두 비교(0.65, 길이 비율 ≥0.5).
- **퍼지·접두 비교는 한글 전용** — 짧은 영단어끼리는 편집거리상 전부
  이웃이라(tax↔tale) 라틴 문자는 정확 일치·포함만 인정한다. 영어
  쿼리는 교정 없이 원문이 다국어 임베딩으로 간다.

### T1 — 시맨틱층 (`src/lib/search/embed-worker.ts`)
- 모델: **어휘 가지치기한 multilingual-e5-small** (37MB int8 ONNX,
  `/static/models/e5-small-ko/` 자체 서빙). 25만 다국어 어휘 중
  한글 전체 + 4자 이하 라틴 + 숫자·문장부호 + 코퍼스 등장 토큰
  38,756개만 유지. **원본과 임베딩 공간 동일**(fp32 코사인 1.0000)이라
  문서 벡터 인덱스를 공유한다.
- 실행: Web Worker에서 transformers.js. WebGPU 어댑터가 잡히면 GPU,
  아니면 WASM, 로컬 모델 실패 시 HF 허브 원본(Xenova/multilingual-e5-small)
  폴백. 최초 로딩 ~4초(같은 오리진 fetch + 브라우저 캐시).
- 검색: 쿼리 임베딩(`query: ` 접두사) × 문서 벡터(785×384 int8,
  벡터당 스케일) 내적 — 1ms 미만.

### 오타 교정 (`core.ts correct()`)

**교정 우선순위** — 아래 순서대로 결정된다.

1. **발동 조건**: 제목 리터럴 일치가 하나라도 있으면 교정 자체가 꺼진다.
   exact 모드(`?exact=1`)에서도 꺼진다. 교정은 아무것도 못 찾을 때의
   최후수단이다.
2. **쿼리 해석 후보**: ① 명사 세트(형태소 분석) ② 표면형 토큰(공백 분리)
   ③ 결합형(공백 제거, 다토큰 쿼리만). 단일 토큰 쿼리에서 명사 커버리지가
   70% 미만이면 명사 세트는 불신("쎄금"→['금'] 파편화 방지).
3. **단어별 교정 후보** (`termsMatch` 점수): 같음 1.0 > 포함 0.9
   (양쪽 2자↑, 쿼리가 삼키는 방향은 60%↑ 덮을 때만) > 자모 오타 0.7 >
   접두 0.65 (길이 비율 ≥0.5). 동점이면 **길이가 쿼리 단어에 가까운 후보**
   ("사유재솬"에 "자유"보다 "사유재산"). 사전 = 코퍼스 단어 + 인접 제목
   단어 결합형(바이그램). 라틴 문자 단어는 퍼지·접두 대상에서 제외.
4. **해석 간 선택**: 품질(단어 평균 점수) 최고 → 동점이면 **원문 글자
   보존이 큰 쪽** ("미제스 코리아 특별카럼"에서 결합형이 "미제스코리아"
   포함 일치로 단어를 통째로 버리는 것보다 "특별카럼"→"특별칼럼" 치환이
   이긴다) → 그래도 동점이면 **토큰이 적은 쪽** ("세 금"의 [세,금]보다
   "세금" 합침).
5. **채택 조건**: 실제 오타 치환 또는 띄어쓰기 결합이 일어났을 때만.
   조사 제거만("자유와 반공을 위해"→"자유 반공"), 글자 동일 분리
   ("라스바드"→"라스 바드")는 교정으로 치지 않는다.
6. **적용**: 교정문으로 시맨틱 재임베딩(새 시퀀스 id로 원문 응답과의
   경합 방지). **서버 결과 0건이면 목록을 교정어로 다시 조회**하되
   URL은 `?query=원문&corrected=교정어` — 검색창·제목에는 사용자가 친
   원문이 그대로 남고, 제목 아래에 **"'교정어'(으)로 검색된
   결과입니다"** 안내와 **"원문 그대로 검색하기"** 링크
   (`?query=원문&exact=1`)가 붙는다.
7. **exact 모드**: 추론 전부 꺼짐 — 형태소·퍼지·시맨틱 없이 제목 리터럴
   포함만, 임베딩 모델도 로딩하지 않는다. 검색창에서 새로 검색하면
   exact가 풀려 교정 시퀀스가 처음부터 반복된다.

## 4. 부가 기능

- **연관 태그 칩**: 쿼리(교정 포함)와 닿는 태그를 결과 상단에 칩으로
  노출, 클릭 시 기존 서버 태그 필터(`?tags=`)로 연결.
- **관련 글 사이드바** (글 페이지): 오프라인 문서 그래프에서 미리 계산한
  글당 top-10 (`src/lib/server/data/related_links.json`)을 SSR로 렌더링.
  서버 연산은 조회뿐.
- 결과 목록은 서버 검색과 동일한 `ArticleListElement` UI(썸네일·게시판·
  조회수·미리보기·태그·저자).

## 5. 메모리 관리 (3중 방어)

WASM 힙은 자라기만 하고 줄지 않으므로 워커 수명으로 관리한다.

1. **검색 10회마다 워커 재활용** — 응답 전달 직후, 대기 요청이 없을 때
   종료 후 즉시 재예열(로컬 37MB라 수 초). 장시간 세션의 누적 상한.
2. **3분 유휴 시 워커 종료** — 실측 약 580MB 반납. 다음 검색 때 자동 재기동.
3. **검색 페이지 이탈 시 즉시 종료**.

가지치기로 활성 메모리 자체도 약 1.3GB → 840MB(WASM 기준)로 감소.
WebGPU 지원 브라우저에서는 가중치가 GPU 메모리로 가서 더 낮다.

## 6. 오프라인 파이프라인 (Mises 작업 레포 `scripts/`)

### update_index.sh 작동 시퀀스 (~5분)

```
scripts/update_index.sh              # 전체 실행 (SSH 비밀번호는 실행 시 입력)
SKIP_FETCH=1 scripts/update_index.sh # 로컬 data.db 재사용
```

| # | 단계 | 스크립트 | 하는 일 |
|---|---|---|---|
| 1 | DB 복사 | `scp` | 서버의 `pocketbase/pb_data/data.db`를 읽기 전용으로 가져온다 (`SKIP_FETCH=1`이면 생략) |
| 2 | export | `export_articles.py` | published 글 → `data/articles/*.json` (HTML 엔티티 복원, 썸네일·미리보기 포함) |
| 3 | 임베딩 ×2 | `embed_articles.py base` / `small` | base = 그래프 kNN용, small = 검색 인덱스용 문서 벡터 |
| 4 | 그래프 | `build_graph.py` | 노드·엣지 재구축 — kNN 엣지도 이때 전부 다시 잇는다 |
| 5 | 인덱스 | `build_index.py` | **node2vec 재학습** + 관련 글 BFS 재계산 + int8 벡터·메타·태그 인덱스 |
| 6 | 그래프 시각화 | `graph_layout.py` + `build_viz.py` | t-SNE 레이아웃 재계산 → `static/admin/graph.html` + `graph-data.json` 갱신 |
| 7 | 프론트 복사 | `cp` | `static/search-index/*`, `src/lib/server/data/related_links.json` 교체 |

끝나면 안내가 출력된다: **프론트 레포에서 diff 확인 → 브랜치에 커밋·푸시
→ 이미지 재빌드·배포**. 배포되면 열려 있는 관리자 그래프
(`/admin/graph.html`)도 1분 내 자동으로 최신 데이터로 다시 그려진다.

주의: node2vec 학습이 멀티스레드라 실행마다 관련 글 순위가 미세하게
달라질 수 있다(품질 동일). 가지치기 모델(`prune_model.py`)은 이 시퀀스에
포함되지 않는다 — 코퍼스 어휘가 크게 바뀔 때만 별도로 재실행하면 된다.

### 자동 재학습 (GitHub Actions, `.github/workflows/index-refresh.yaml`)

수동 실행(`update_index.sh`) 외에, **매시간** 공개 API로 글의 내용
필드(제목·본문·태그·게시판·분류·미리보기) 해시를 검사해
(`pipeline/check_source.py`) 추가·수정·삭제가 감지되면 — slug 변경·
조회수·썸네일 교체는 의도적으로 무시한다 — 러너에서 전체 재학습(`pipeline/ci_refresh.sh` — API
export → 전체 재임베딩(CPU, 증분 없음) → node2vec 재학습 → 인덱스·그래프·
폴백 자산)을 돌리고 결과를 **PR로 올린다. 머지는 사람이 한다** —
머지되면 기존 CI가 이미지를 빌드한다. 서버 접근·시크릿이 전혀 필요 없다
(모든 데이터가 공개 API).

**새 글을 올린 직후 바로 반영하고 싶을 때**: GitHub → Actions →
Index Refresh → **Run workflow** (또는 `gh workflow run index-refresh.yaml`).
`force`를 켜면 변화가 없어도 강제 재학습한다.

주의: 스케줄·수동 실행 모두 워크플로 파일이 **기본 브랜치(main)에 있어야**
활성화된다 — 이 브랜치가 머지된 시점부터 동작한다. 소요: 감지만 하고
끝나면 ~1분, 재학습 포함 ~15-20분(CPU 재임베딩; 로컬 Mac은 GPU라 ~5분).

### 스크립트별 산출물

| 스크립트 | 산출물 |
|---|---|
| `export_articles.py` | 글 785건 JSON (HTML 엔티티 복원, 썸네일·미리보기) |
| `embed_articles.py [small\|base\|large]` | 512토큰 이하 청크 → 문서벡터(정규화 평균) |
| `build_graph.py` | 노드 932 + 엣지 1.58만 (내부링크·텍스트 kNN·저자·태그·시리즈) |
| `related_search.py` | node2vec 유사도 가중 BFS 빔서치 |
| `build_index.py` | int8 문서벡터·메타·태그·관련 글 (총 ~1.9MB) |
| `graph_layout.py` / `build_viz.py` | t-SNE 레이아웃 → 관리자 그래프 페이지 |
| `prune_model.py` | 어휘 가지치기 ONNX (시퀀스 밖, 필요 시만) |

node2vec은 transductive라 새 글 노드는 재학습 전까지 임베딩이 없다 —
그래서 증분 갱신 대신 전체 재학습을 쓴다(전체 5분이라 증분 설계가 무의미).

### 알고리즘 선정 근거 (held-out 링크 예측, R@10)
node2vec **0.811** > PPR 0.769 > GraphSAGE 0.694(기각: 베이스라인을
이기지 못함) > 텍스트 단독 0.419. 서빙은 BFS(0.788)로 — 그래프 이웃
제한과 추천 근거 설명 가능성 때문.

|---|---|---|
| 정상 | 0.727 | **0.880** |

## 8. WASM 차단 환경 폴백 (락다운 모드 등)

기본 경로는 WASM/WebGPU이고, **로딩이 실패할 때만** 우회 자산을 lazy로
받아 순수 JS로 동작한다 — 평소 사용자는 아무것도 더 받지 않는다.

| 기능 | 기본 경로 | 차단 시 폴백 |
|---|---|---|
| 문서 토큰화·교정 사전 | garu(WASM)가 브라우저에서 계산 | 파이프라인이 미리 계산한 `terms.json`(64KB) fetch |
| 쿼리 명사 추출 | garu | 규칙 기반 조사 제거(`stripParticle`) |
| 오타 교정 | (위 사전으로 동일 동작) | 동일 — "쎄금"→"세금" 그대로 작동 |
| 시맨틱 검색 | e5 ONNX (WASM/WebGPU) | **합성 임베딩**: 어휘 단어별 e5 벡터 표(`vocab_vectors_i8.bin`, 1.8MB)에서 쿼리 단어 벡터 평균 — 문서 벡터와 같은 공간이라 융합·게이트 그대로 |

한계: 합성 임베딩은 어순·문맥을 잃으므로 긴 자연어 질문에서 정밀 모델보다
약하다. 상태 안내는 "정밀 의미 검색 모델을 쓸 수 없어 간이 검색으로
동작합니다"로 표시된다. 폴백 자산은 `pipeline/build_terms.js`(node·garu) +
`pipeline/build_fallback_vectors.py`가 만들고 `update_index.sh`에 포함된다.

## 9. 보류된 계획 (더 좋은 서버 확보 시)

SSR 성능 개선은 **보류** (2026-08 결정). 현 서버가 RAM 756MB에 가용
~100MB, 스왑 사용 상태라 서버에 일을 더 얹는 방향은 성립하지 않는다 —
그래서 검색도 전부 브라우저·정적 파일로 설계했다. 서버를 업그레이드하면
다시 꺼낼 후보들:

- **서버사이드 쿼리 임베딩** — 방문자 브라우저의 모델 다운로드(37MB)와
  메모리 점유가 사라진다. e5-small 추론에 RAM 여유 2GB+ 필요.
- **SSR 성능 측정·최적화** — `pipeline/bench_ssr.py`(표준 라이브러리만,
  서버에서 직접 실행)로 기준선을 잡고 시작하면 된다.
- 검색 인덱스·관리자 그래프의 서버 직접 서빙(배포 없이 갱신), 응답 캐싱 등.
